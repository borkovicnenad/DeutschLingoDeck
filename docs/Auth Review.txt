AuthenticationServiceImpl is fully implemented and verified live against Postgres via docker-compose (register → login → me → refresh → logout, plus the 401/409 error paths). Here's what's happening and why:

The gap that had to be filled first
None of this existed: no JWT library dependency, no token provider, no users/refresh_tokens tables (Flyway migrations dir was empty, ddl-auto: none), and the security filter chain was permitAll() everywhere. Implementing the service meant building the whole stack under it.

Design decisions worth flagging
- Refresh tokens rotate: every refresh() call revokes the presented token and issues a new one. Reusing an old one → 401. Verified in the smoke test.
- Login/refresh use one generic message ("Invalid email or password" / "Invalid or expired refresh token") regardless of why it failed, to avoid leaking whether an email is registered.
- getCurrentUser()/logout() re-read the user from SecurityContextHolder's principal (just the user id), not from JWT claims directly — keeps /me responses accurate even if a display name changes mid-token-lifetime.
- logout() revokes all active refresh tokens for the user, not one specific token — the OpenAPI /auth/logout request has no body, so there's no way to identify a single session/token.
- Access tokens are not revocable (stateless by design) — logging out doesn't kill an already-issued access token before its 15-min TTL expires. This is standard for short-lived access tokens; only the refresh token (the thing that grants long-term renewal) is tracked and revoked.
- This flips security for every other controller too (dictionaries/games/statistics/profile), since they were all permitAll() before. That's intentional and matches the OpenAPI spec's global bearerAuth requirement — but it means the frontend's dev-mode bypass (fake login, no real JWT) will now get real 401s from those endpoints instead of whatever they returned before. The frontend's sample-data fallback already handles that gracefully.

One thing to flag: the JWT secret has a dev-only default in application.yaml (JWT_SECRET env var overrides it) — fine for local/docker-compose, but must be set explicitly before any real deployment.
